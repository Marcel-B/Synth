# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

Tonwerk Synth: the two browser synthesizers of Tonwerk (repository `Marcel-B/Tonwerk-AI`, formerly `YuE-UI`, `src/YueUI.Api/ClientApp/src/logic/synth.ts`, `fm.ts`, `envelope.ts`, `effects.ts`) as JUCE instrument plugins for Logic Pro: Tonwerk Analog (`aumu TwAn Bvlp`) and Tonwerk FM (`aumu TwFm Bvlp`), plus Tonwerk Synth (`aumu Twsy Bvlp`), the first plugin with both engines, kept so Logic projects made with it still open. Audio Unit (v2 component, the format Logic loads), VST3 and a standalone app from one CMake project. README.md (German) is the user documentation.

## Commands

Requires CMake 3.22+ and a C++20 compiler; JUCE 8 comes through `FetchContent` (pinned tag in `CMakeLists.txt`). On Linux, JUCE needs the packages listed in `.github/workflows/build.yml`.

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug     # add -DFETCHCONTENT_SOURCE_DIR_JUCE=<clone> to reuse a local JUCE
cmake --build build --target TonwerkSynthTests && ctest --test-dir build --output-on-failure
cmake --build build --target TonwerkAnalog_Standalone     # also TonwerkFM_*, TonwerkDX_*, TonwerkSynth_*, *_VST3, *_AU (macOS only)
scripts/install-macos.sh                                  # on the Mac: Release build, ad-hoc signing, install, auval
scripts/build-ios.sh simulator                            # the iPad app Tonwerk (every AUv3 inside), needs full Xcode; `device` with TONWERK_TEAM_ID
```

The Mac has only the Command Line Tools, no Xcode: keep the build on CMake's default generators, never require the Xcode generator, an AUv3 app extension or a signing identity. The one exception is the iPad build (`-G Xcode -DCMAKE_SYSTEM_NAME=iOS`, `scripts/build-ios.sh`): format AUv3 only, `TONWERK_IOS_OPTIONS` on every `juce_add_plugin` (a new plugin gets the line), bundle ids under `TONWERK_BUNDLE_PREFIX` (an extension's id must be its app's plus exactly one part, so each `<Target>_AUv3` takes its plugin's id, not JUCE's `<id>.<last>AUv3`; ITMS-90347), no tests. All AUv3s go into one app, `Tonwerk` (`app/src/`, `juce_add_gui_app`, bundle id `de.bvelop.tonwerk`, opaque icon `icons/Tonwerk.png` from `APP_ICONS` in `make-icons.py`): its `XCODE_EMBED_APP_EXTENSIONS` lists every `<Target>_AUv3` (a new plugin goes there, into `TONWERK_ALL_SOURCES` and, if it plays alone, into `app/src/Catalogue.cpp`), each bundle carries `app/PrivacyInfo.xcprivacy`, and on its own it plays one instrument at a time (of the effects only Tonwerk Scope, `Entry::listens`: the input in, the output kept from the speakers, `Eingang` opens the device selector; the editor at the top, cut off above its own keyboard, under it the app's keyboard of two octaves with octave buttons and a scope, `Tasten` hides them) from the same sources as the tests (the `*_NO_ENTRY` defines; `-DTONWERK_APP=ON` builds it on the desktop, `TONWERK_PLUGIN=<name>` opens that plugin). CI's `ios` job builds it for the simulator, checks the 34 AUv3s and uploads simulator screenshots (`ipad-screenshots`); `testflight.yml` (by hand) archives it with cloud-managed signing (API key secrets `ASC_KEY_ID`, `ASC_ISSUER_ID`, `ASC_KEY_P8`, Admin role, plus `APPLE_TEAM_ID`) and uploads it, build number `TONWERK_BUILD_NUMBER` from the run number. `common/Platform.h` holds what differs there: `createEditor` returns `tonwerkui::forHost(new XEditor(*this))` (on iOS a `TouchFrame` that scales the editor to the host's size), popup menus open inside the editor (`menuParentFor` in the look and feels), files the user chooses are read and written through the chooser's URL (`readChosenText`, `writeChosenText`, `keepChosen` copies samples into the container, `findKept` finds them after iOS moved it), and a held finger on a knob opens the MIDI menu. The Mac App Store's build is the same app for macOS (`-G Xcode -DTONWERK_MAC_STORE=ON`, so `TONWERK_STORE` like iOS: AUv3 only, ids under the app's, no tests): every bundle sandboxed (`APP_SANDBOX_OPTIONS` network client and user-selected files, appended last to `TONWERK_IOS_OPTIONS` so the app adds audio-input), `LSApplicationCategoryType` music, and `TONWERK_SANDBOX=1`, under which `Platform.h` copies chosen files into the container and opens menus inside the editor as on iOS; CI's `macstore` job builds it signed to run locally, checks the 34 sandboxed AUv3s and uploads store screenshots of the 1280 x 800 window content (`mac-screenshots`), `testflight.yml` uploads it beside the iPad build (matrix, input `platforms`). Its AUv3s share the AU v2 components' codes, so the store app and `install-macos.sh`'s components must not both be installed. Built only in CI, not yet uploaded or run. Not yet run on a real iPad or in Logic Pro for iPad; the first TestFlight upload (0.5.0, build 2, 2026-10-17) was refused for its extension ids and for the iOS 18.5 SDK; App Store Connect takes only Xcode 26 or later, so the `ios` job and `testflight.yml` pick the runner's newest Xcode. `testflight.yml` signs nothing with the team in the archive (iPad unsigned, Mac ad hoc so the export keeps the sandbox entitlements; a signed archive made every fresh runner create an Apple Development certificate until the account's limit), only `-exportArchive` signs, with the API key and the cloud-managed distribution certificate, and fetches the 35 profiles. Releases: pushing a tag `v*` runs `release.yml` (or starting it by hand with a version, which then makes the tag; the cloud sessions cannot push tags), which builds with `-DTONWERK_VERSION` from the tag, signs (`scripts/sign-macos.sh`: Developer ID with hardened runtime when the secrets `MACOS_CERTIFICATE_P12`/`MACOS_CERTIFICATE_PASSWORD` are set, notarized by `scripts/notarize-macos.sh` when `APPLE_ID`/`APPLE_TEAM_ID`/`APPLE_APP_PASSWORD` are too, ad hoc otherwise), runs auval and attaches a zip (plugins, app, `scripts/install-release.sh` as `install.sh`, which removes the quarantine flag) to a GitHub release, next to a Linux tar.gz and a Windows zip (VST3 and standalone apps, built without tests and packed by `scripts/package-release.sh`, which takes every `*_artefacts/Release`; Linux adds `scripts/install-linux.sh`; Windows links the C++ runtime statically and is unsigned). `release-stats.yml` appends every release package's download count daily to `downloads.csv` on the branch `stats` (`scripts/release-stats.sh`; GitHub keeps only running totals). CI (`build.yml`) builds without LTO (`-DTONWERK_LTO=OFF`, so ccache/sccache can keep the objects between runs; with LTO every link generates all code again) and runs the tests on Linux and on macOS, builds and packages the Windows VST3s (no tests), builds the universal AUs there, signs them ad hoc and runs `auval -strict -v` on every plugin. Warnings come from `juce_recommended_warning_flags`; keep the build free of them.

## Architecture

- `src/dsp/` is plain C++ without JUCE: `Patch.h` (the patch as Tonwerk's JSON describes it, both engines plus effects, and the TX81Z algorithm table), `Defaults.cpp` (Tonwerk's starting sound per track kind), `Ranges.h` (every range, the same as Tonwerk's `RANGES`, `FM_RANGES`, `EFFECT_RANGES`), `Envelope.h`, `Oscillators.h` (PolyBLEP oscillators, LFO, Web Audio's biquad, noise), `AnalogVoice.h`, `FmVoice.h`.
- The aim is to sound like the browser. Each DSP class says in its comment which Web Audio behaviour it reproduces (the pulse built from two sawtooths is half as loud as the plain square, lowpass/highpass Q is decibels, the envelope's time constants, FM in Hz with `kMaxIndex` 8, feedback averaged over two samples, reverb level 0.15). When Tonwerk's synths change, change both, and keep `PatchJson.cpp` reading their JSON.
- `PatchJson.cpp` reads and writes Tonwerk's patch JSON the way its `normalizePatch` does (missing fields take the melody's default, ranges clamp, `engine` absent means analog). Importing one engine keeps the other's settings.
- The three synth plugins are one set of sources built three times (`tonwerk_add_synth` in `CMakeLists.txt`, `TONWERK_EDITION`); `TonwerkSynthProcessor(Edition)` decides. Each descriptor has a `Part` (engine switch, analog, fm, effects, from its id); an edition gets only its parts' parameters (`createParameterLayout(edition)`), `ParameterReader` leaves the missing fields at their defaults, and the one-engine editions force `patch.engine`. Their state roots are `TonwerkAnalog` / `TonwerkFM`; Tonwerk Synth keeps `TonwerkSynth`. Factory sounds per edition (`PresetLibrary::factoryPresets(edition)`): Tonwerk's four per engine first, then the plugin's own (`FactorySounds.cpp`, plain C++, new ones at the end); Tonwerk Synth keeps its first eight program numbers. The imported library is shared, `importedFor(edition)` filters by engine.
- `Parameters.cpp` has one table (`descriptors()`) of every patch field as a host parameter; layout, reading a `Patch` from the parameters each block (`ParameterReader`) and writing an imported patch (`writePatch`) all come from it. A new field is one entry there. Parameter ids are part of saved Logic projects: never rename or remove one, and append new ones with the version hint of the release they first appear in (2 for 0.2.0, 3 for 0.3.0).
- `PluginProcessor.cpp`: a `juce::Synthesiser` with 16 `SynthVoice`s rendering mono into a buffer, then `EffectsChain` (delay, `juce::dsp::Convolution` reverb) into stereo. Voices read the shared patch every block, so knobs act on sounding notes. The reverb's impulse is made on the message thread (timer), never on the audio thread.
- Wavefolder and sample and hold (`AnalogPatch::fold`, `sampleHold`; `Wavefolder`, `SampleHold` in `Oscillators.h`) are the plugin's own, not Tonwerk's: the folder sits between the oscillator mix and the filter, the sample and hold moves cutoff and pitch per voice. Both are off at their defaults, `patchToJson` writes them only when on, and a Tonwerk sound imports with them off.
- Tempo sync (`dsp/Tempo.h`, `withTempo`): the processor turns a synced LFO's or sample and hold's note value into a rate and a synced delay's into a time, from the play head's BPM (120 without one), before the voices and effects see the patch; the DSP knows only rates and times. Sync and division are this plugin's own fields; Tonwerk's JSON lacks them, `patchToJson` writes them only when sync is on.
- `ScopeBuffer` (`common/ScopeBuffer.h`, a processor member) holds the last 4096 output samples as atomics; `ScopeView` (`common/NightCity.h`) reads them at 30 Hz and triggers on a rising zero crossing, as Tonwerk's `SynthScope.vue` does.
- `common/NightCity.{h,cpp}` is the look every plugin but Chrome Glitch uses (Tonwerk Wavetable's): colours, `LookAndFeel`, `Control` (knob, menu or switch for a parameter), `Section` (panel of rows, optional power switch and display room on the left or on top, `when` to swap a rate knob for its note value), `layoutRow` (spare width goes to panels with a display), `ScopeView`. Values are shown by the parameters' own text functions: whole numbers with units.
- Factory sounds of all five synths carry a category from `common/PresetCategories.h`; the editors' menus group by it (`menuOrder`), the program numbers stay in release order. `tests/PresetTests.cpp` plays each with a phrase of its category and holds it to one loudness (EBU momentary max: −12 LUFS, Tonwerk DX −16 because a voice ends at half of full scale, ±2 dB, effects up to 6 dB lower) and a peak under 1.0 with delay and hall; Tonwerk's own starting sounds and Init are exempt. A new sound is leveled with its volume (DX also against `DxTests`' hard chord). `TONWERK_PRESET_WAV_DIR=<dir>` writes each phrase as a WAV, `TONWERK_TEST_CATEGORY=Presets` runs only that category. The hall seeds its noise with the room size, so a sound measures and bounces the same every time; the test waits for the convolution to take the room over (`roomPlaying`).
- `common/MidiLearn.{h,cpp}`: MIDI learn in every plugin that takes MIDI (the instruments, Robovox, Vocoder, Arp): a `midiLearn` member after `state`, `midiLearn.process(midi)` first in `processBlock`. The map is a child `MidiMap` of the parameters' tree (`cc20` = `cutoff`), so projects keep it and presets leave it; the audio thread reads it from atomics and calls `setValueNotifyingHost`. CC 0-31 take a fine half on +32 (14 bits); 120-127 and the fine halves are never learnt. `Control` (NightCity) finds the instance with `MidiLearn::of(state)` and offers learn/forget on a knob's right click, its name showing `· CC20`. A new instrument gets the member and the call.
- `common/EffectPresets.{h,cpp}`: the effects' factory sounds as host programs (`EffectPrograms`, a sound names only what it changes from the defaults, its name kept in the state as `presetName`) and the header's preset menu with arrows (`PresetBar`). `tests/EffectPresetTests.cpp` (category Presets) checks and levels them; `TONWERK_PRESET_WAV_DIR` writes their takes and the dry sources.
- `PresetLibrary.cpp`: factory sounds (the host's programs) and imported ones in `presets.json` under Application Support, plus Tonwerk's address in `settings.json`. `fetchFromTonwerk` calls Tonwerk's `GET /api/logic/synths/presets` (no login, reached over Tailscale).
- `PluginEditor.cpp`: sections per engine (envelope displays, the FM algorithm drawn by `AlgorithmView`), the engine switch for Tonwerk Synth only (its editor resizes per engine), the preset menu and the import/export buttons, an on-screen keyboard and the scope. Strings with umlauts go through `utf8()` / `String::fromUTF8`, since `juce::String` reads a plain `const char*` as ASCII.

## Chrome Glitch

A second plugin in the same CMake project: `ChromeGlitch` (audio effect, `aufx ChGl Bvlp`, sources in `glitch/src/`, tests in `tests/GlitchTests.cpp` inside `TonwerkSynthTests`). It is built, signed, validated with auval, installed and released alongside the synth. `GlitchEngine.h` is plain C++: ticks (grid lines of the host tempo in sync, random 40-250 ms gaps otherwise, the chaos share of those also in sync) roll for a stutter (replays the last slice, later repeats maybe pitched, never wrapping inside a repeat) or a dropout; every change crossfades over 1.5 ms; the crusher is full during a glitch and light between. While the host plays with a position, the dice (and the crusher's hold phase) reseed at every beat from the `seed` parameter and the beat number, so a glitch belongs to its place in the song whatever the start point; without a position they seed once per transport start. Its parameter ids follow the same never-rename rule; they start at version hint 1 (`seed` has 2). The test app defines `CHROME_GLITCH_NO_ENTRY` because both plugins define `createPluginFilter`. The editor uses Cyberpunk 2077's colours (yellow, cyan, red on near black); its `GlitchMonitor` reads `glitching`, `glitchStarted` (set by the processor whenever `GlitchEngine::eventsStarted()` grows, taken back by the editor's 30 Hz timer, so a glitch shorter than a frame still shows) and `lastEvent`. The monitor's texts (CHROME OK, INTERFERENCE, NO SIGNAL, FROZEN) are English on Marcel's wish, the one exception to German UI strings. Factory presets (`GlitchPresets.cpp`, groups `kGlitchCategories`) are tested to glitch on a voice, never louder than it and at most 3 dB quieter.

## Tonwerk Distortion

A third plugin in the same CMake project: `TonwerkDistortion` (audio effect, `aufx TwDs Bvlp`, sources in `distortion/src/`, tests in `tests/DistortionTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the other two. `Ds1Circuit.h` is plain C++: BOSS DS-1's circuit with ElectroSmash's part values, in volts (1.0 = 1 V at the jack). `Drive` (booster, op-amp stage, rails, diode clipper from a Shockley table) runs 4x oversampled through `juce::dsp::Oversampling` (polyphase IIR) with first-order ADAA on both clippers; `Voice` (tone blend, level, DC block) runs at the host rate. The op-amp's slew rate is deliberately left out (it aliased more than all the clipping). Beside the pedal, `mode` (version hint 2, a menu: append only) picks one of four curves in `Shapers.h` for electronic sounds: tube (biased soft clip, even harmonics), clipper (hard clip), folder (sine wavefolder), rectifier (lower half flipped up at half its size, octave fuzz), crusher (`Crusher`: DIST takes the bits from 16 to 2, `crushRate` holds at 500 Hz to 48 kHz; no gain, its level follows the input, its images are wanted); each curve is a `Shaper` (gain up to 30 dB, 24 for clipper and rectifier, ADAA, output scaled to the pedal's level) in the same 4x oversampling. `Distortion` holds all of them per channel, runs only the chosen one and cross-fades old and new over 20 ms on a change; `Voice` gives the pedal its tone blend and the other modes a ±6 dB tilt around 700 Hz, both always running, blended by mode. Keep CPU low: the test logs the real-time factor. `mix` (dry/wet, version hint 2 like `crushRate`) blends after `Voice`; the dry side goes up and down through a second oversampler so both sides share delay and phase and do not comb. The editor (Night City) shows `scopeOut` over `scopeIn`, the input read `getLatencySamples()` behind. Factory presets (`DistortionPresets.cpp`, groups `kDistortionCategories`) are leveled with `level` to match their dry source (a test signal of their group peaking at -6 dBFS) within 2 dB. Parameter ids start at version hint 1; the test app defines `TONWERK_DISTORTION_NO_ENTRY`.

## Tonwerk Wavetable

A fourth plugin in the same CMake project: `TonwerkWavetable` (instrument, `aumu TwWt Bvlp`, sources in `wavetable/src/`, tests in `tests/WavetableTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. A wavetable synth in the manner of Serum, for dubstep basses; nothing of Serum's (tables, presets, art) is copied. `Wavetables.cpp` computes every table from a formula at load (64 frames, one band-limited copy per octave, shared by all instances); `WaveDsp.h` and `WaveEngine.h` are plain C++ (envelopes, LFOs, TPT state variable filter, comb, voices, poly/mono/legato, matrix). Modulation runs every 32 samples with ramps in between; keep it that way for CPU. The sub oscillator and noise come from `src/dsp/Oscillators.h`. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them: a new parameter goes at the end of both. Factory sounds are in `WavetablePresets.cpp` as changes from the defaults. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_WAVETABLE_NO_ENTRY`.

## Tonwerk DX

A fifth plugin in the same CMake project: `TonwerkDX` (instrument, `aumu TwDx Bvlp`, sources in `dx/src/`, tests in `tests/DxTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. Six operators in the DX7's 32 algorithms (Tonwerk FM stays at four so Tonwerk's JSON stays 1:1). `DxEngine.h` is plain C++ in the DX7's units: levels and rates 0 to 99, a level step 0.75 dB, envelopes in the log domain, envelopes and LFO every 32 samples with gain ramps between, a sine table; keep it that way for CPU. `lfoHz` is fitted to DX7/TX7 measurements (speed 35 about 5.6 Hz, 99 about 49 Hz), so SysEx vibratos run at their speed. `DxSysex.h` reads DX7 banks and single voices the user owns (pitch EG, keyboard level scaling and fixed frequencies are dropped); imported files live in Application Support/Tonwerk DX/SysEx. Factory sounds (`DxPresets.cpp`) are the plugin's own, never copies of Yamaha's ROM; new ones go at the end. `DxProcessor.cpp` has one table (`parameters()`) of every patch field; ids start at version hint 1. The delay and hall are the synth's `EffectsChain`. The test app defines `TONWERK_DX_NO_ENTRY`.

## Tonwerk Granular

A sixth plugin in the same CMake project: `TonwerkGranular` (instrument, `aumu TwGr Bvlp`, sources in `granular/src/`, tests in `tests/GranularTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. `GrainSources.cpp` computes nine sources from formulas at load (4 s each at 48 kHz, root C4, shared by all instances) plus copies at half, quarter, ... rate, each lowpassed, so a grain read faster than its source takes the copy that keeps it below Nyquist; the user's file (`loadFile`, first 30 s, mono) gets the same treatment, its path is in the state (`sampleFile`) and is read again on load, the samples are not saved. The message thread swaps the user's source under a spin lock, the audio thread takes it with a try-lock, and a replaced source waits in `retired` until only that list holds it, so the audio thread never frees one. `GranularEngine.h` is plain C++ and borrows `Adsr`, `SvfStage` and `lfoShape` from Tonwerk Wavetable's `WaveDsp.h`: up to 40 grains per voice, windows from tables, a cloud's level scaled by 1/sqrt of the overlap so density and size keep the loudness, modulation every 32 samples, fixed routes (two LFOs, envelope 2, wheel, velocity) to one target each. A grain's start is chosen so it fits in the source without wrapping. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them, the `fx*` ones (Tonwerk DX's ids, read apart) left out: a new parameter goes at the end of both. Delay and hall are the synth's `EffectsChain` with its stereo overload. Factory sounds (`GranularPresets.cpp`) are changes from the defaults, leveled to −12 LUFS by `PresetTests`. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_GRANULAR_NO_ENTRY`.

## Tonwerk Physical

A seventh plugin in the same CMake project: `TonwerkPhysical` (instrument, `aumu TwPh Bvlp`, sources in `physical/src/`, tests in `tests/PhysicalTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. `PhysicalEngine.h` is plain C++ and borrows `Adsr`, `SvfStage` and `lfoShape` from `WaveDsp.h`: an exciter (pluck, strike, bow, blow) drives a resonator. String and tubes are waveguides (two delay lines meeting at the excitation point, Lagrange fractional delay, a one-pole loss filter set from two T60s, four allpasses for a stiff string's stretch, the loop's delay compensated so the note stays in tune); the bow is a friction curve on the string's velocity, the reed a pressure curve on a closed tube. Bar, bell, membrane and bowl are up to 16 two-pole resonators from `modeTable`. `levelOf` and the drive normalisation keep every exciter on every resonator within a few dB of each other at the defaults; tests hold each pairing finite and bounded at the extremes. Modulation every 32 samples with ramps; keep it that way for CPU. Enum orders are menu orders saved in projects: append only. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them, the `fx*` ones (Tonwerk DX's ids) left out: a new parameter goes at the end of both. Factory sounds (`PhysicalPresets.cpp`) are changes from the defaults, leveled to −12 LUFS by `PresetTests`, new ones at the end. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_PHYSICAL_NO_ENTRY`.

## Tonwerk Additiv

A further plugin in the same CMake project: `TonwerkAdditiv` (instrument, `aumu TwAd Bvlp`, sources in `additive/src/`, tests in `tests/AdditiveTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. `AdditiveEngine.h` is plain C++ and borrows `Adsr` and `lfoShape` from `WaveDsp.h`: up to 64 sine partials per voice, each a complex phasor turned by a fixed rotation per sample (no sine calls; renormalised once per step), eight partials side by side in lanes so the compiler vectorises them (keep that loop shape: it made the engine half again as fast), only the partials that sound and lie below 0.47 fs are computed. All shaping is a gain per partial, set every 32 samples with linear ramps between (`levelsOf`): two spectra from `spectra()` (formulas, each scaled to the same RMS) morphed, partial count (fractional), odd/even, tilt (energy kept, so it never makes a note louder), comb, vowel formants fixed in hertz, and the filter (24 dB/oct, resonance a peak), so the filter can neither ring nor alias. Stretch and beating move each partial's ratio (`ratioOf`); the rotations are only recomputed when pitch or ratios change. Each partial may have its own envelope (bloom, decay scaled by k^damping, sustain). Enum orders are menu orders saved in projects: append only. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them, the `fx*` ones (Tonwerk DX's ids) left out: a new parameter goes at the end of both. Factory sounds (`AdditivePresets.cpp`) are changes from the defaults, leveled to −12 LUFS by `PresetTests`, new ones at the end. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_ADDITIVE_NO_ENTRY`.

## Tonwerk Groovebox

An eighth plugin in the same CMake project: `TonwerkGroovebox` (instrument, `aumu TwGb Bvlp`, sources in `groovebox/src/`, tests in `tests/GrooveboxTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. A drum machine: eight synthesised instruments (no samples) and a step sequencer. `GrooveEngine.h` is plain C++ and borrows `Biquad`, `Noise` and `BlepOscillator` from `src/dsp/Oscillators.h`: each `Voice` builds its instrument the way the analog drum machines do (falling sine for kick and toms, body plus filtered noise for the snare, noise bursts for the clap, six squares at the 808's ratios band-passed for hats and cymbal), `decay` is the time to -60 dB; each track has two voices so a new hit lets the last fade over 5 ms; the closed hat chokes the open one. `Clock::steps` counts steps from the song's beat 0 (so patterns sit on the host's bars, whatever the start or loop), swing delays every odd step. The processor runs it from the play head's ppq (`seqMode` host, only while playing), from its own beat counter (free) or not at all; a block that starts within half a sample of the last one's end continues it, so a step on the seam plays once. MIDI notes play tracks on General MIDI's drum notes (`trackForNote`). `roll` (global) plus `<track>Roll` (version hint 4) vary the pattern through `rollStep`, dice hashed from the step counted from beat 0 and the track, so a bounce repeats. `fxOn` (version hint 4) fades delay and hall out over 20 ms and clears them once silent; kits leave it as it is. Patterns are not parameters: eight per instance, in atomics (on bits low, accent bits high) and in the state as child `Patterns`; the editor's edits call `patternsChanged()` so the host marks the project modified. Per-track delay and hall sends go through `EffectsChain`'s send overload. Besides the main output each track has a stereo output (`buses()`, off by default, Logic's multi-output variant, used by Tonwerk Rig): a track whose output is on renders there (`Engine::render`'s `trackOut`) and leaves the main mix; its sends still feed the shared delay and hall, drive and master apply to it too. Kits (`GroovePresets.cpp`, groups `kGrooveCategories`) name parameter changes and patterns as text (`x`, `X` accent, `.`); choosing one resets everything but `seqMode` and the machines. Each track picks a `Machine` (`<track>Machine`, version hint 3; names in `kMachineNames` lean on classic drum machines but never use their names or trademarks): `voicingFor` gives the instrument's constants (`Voicing`: pitch, sweep, click, noise filters, clap hands, metal ratios, the sampling machines' bits and rate, which join the track's crusher, the coarser counting); `Machine::tonwerk` is `tonwerkVoicing`, the sound from before, so old projects sound the same. `kMachineLevels` matches each machine's instruments to Tonwerk's loudness; the test holds them within 1 dB, so retune it after changing a voicing. `GrooveboxTests` plays two bars of each kit's pattern A and holds it to -16 LUFS momentary ±2 dB with the peak under 1.0 (drums peak about 15 dB over their loudness), new kits at the end. Parameter ids (`kick`, `snare`, `clap`, `tomLow`, `tomHigh`, `hatClosed`, `hatOpen`, `cymbal` + `Tune`, `Decay`, ...) and menu orders start at version hint 1 (the machine menu is append-only too); the test app defines `TONWERK_GROOVEBOX_NO_ENTRY`.

## Tonwerk Robovox

A ninth plugin in the same CMake project: `TonwerkRobovox` (music effect, `aumf TwRv Bvlp`, so Logic can send it MIDI through the side chain; sources in `robovox/src/`, tests in `tests/RobovoxTests.cpp` inside `TonwerkSynthTests`, its presets in `EffectPresetTests`), built, signed, validated, installed and released like the others. Per band: a detector averaging the louder side's power (`kDetectorTime`, read 3 dB up so a sine reads its peak), a soft-kneed curve (`changeFor`: ratio above the threshold, `upward` below it, at most `kMaxBoostDb` 18, fading out under −60 dBFS), the change smoothed in dB (attack down, release up), scaled by the global `depth`; a band switched off passes untouched, solo plays only the soloed ones. Everything per sample. Latency 0. Factory presets (`MultibandPresets.cpp`, groups `kMultibandCategories` in `MultibandPresets.h`) are leveled with `output` to a mix loop at 120 BPM, −6 dBFS peak, within 2 dB; `TONWERK_MULTIBAND_WAV_DIR=<dir>` writes those takes. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them: a new one goes at the end of both. Parameter ids start at version hint 1; the test app defines `TONWERK_MULTIBAND_NO_ENTRY`.

## Tonwerk Zone

A further plugin in the same CMake project: `TonwerkZone` (audio effect, `aufx TwZn Bvlp`, sources in `zone/src/`, tests and its presets' levels in `tests/ZoneTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. A compressor on one range of the spectrum (a dynamic EQ, de-esser), with a side chain bus as Tonwerk Glue's. `ZoneEngine.h` is plain C++ and borrows `SvfStage` from `wobble/src/WobbleEngine.h`: one SVF per side splits into low, band and high, which sum back to the input; the range (`shape`: bell, low or high shelf; `width` in semitones sets the bell's damping) is turned down by how they are summed (bell x − (1 − g)·k·bp, low shelf x − k(1 − √g)·bp − (1 − g)·lp, high mirrored), so below the threshold the output is the input to the bit, the gain moves per sample without new coefficients and `mix` never combs. `mode` Band turns down the range, Breitband everything. The detector averages the louder side's power of the range (of the input, or of the side chain through its own SVF) over about two cycles of `frequency`; reduction soft-kneed, at most `range`, smoothed in dB. `listen` plays the detector's signal. `responseDb` is the analog response for the editor's curve. An LFO (Tonwerk Filter's shapes, `lfoValue`/`randomFor`, and Wobble's divisions; synced to the play head's ppq while playing) moves `frequency` by up to `lfoDepth` semitones (version hint 1, appended; default 0): at depth 0 the coefficients stay per block and the output is bit for bit the old one, with depth they follow every `kLfoStep` (16) samples, the offset smoothed over 3 ms; the processor publishes the moved frequency for the editor. Latency 0. Factory presets (`ZonePresets.cpp`, groups `kZoneCategories` in `ZonePresets.h`) are leveled with `output` to a mix loop at 120 BPM within 2 dB (side chain presets without a key); `TONWERK_ZONE_WAV_DIR=<dir>` writes those takes. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them: a new one goes at the end of both. Shapes, modes and sources are menus saved in projects: append only. Parameter ids start at version hint 1; the test app defines `TONWERK_ZONE_NO_ENTRY`.

## Tonwerk Scope

A further plugin in the same CMake project: `TonwerkScope` (audio effect, `aufx TwSc Bvlp`, sources in `scope/src/`, tests in `tests/ScopeTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. An oscilloscope; the audio passes untouched (tests hold it bit for bit), latency 0. `ScopeEngine.h` is plain C++: `Ring` (the last 65536 samples of both sides as atomics, written by the audio thread), `BeatTrace` (1024 columns of min/max per side over a window of `kWindowBeats`, placed by the play head's ppq while playing, by its own beat at the tempo otherwise; a column is reset when the beat enters it), `findTrigger` (latest crossing in the chosen direction that goes clearly past, a twentieth of the swing, before turning back), `PitchEstimator` (YIN on a copy decimated to about 12 kHz, 30 Hz to 1.5 kHz; `refine` searches the difference function again at the full rate on a two-sample mean, under a cent from 31 Hz to 1.3 kHz) and note names as Logic writes them (C3 = 60), `tuningOf` against `reference` (Kammerton, appended). The editor (`ScopeScreen`, 30 Hz, only while showing) reads the ring and draws the wave, the bars or a goniometer with a glow (or, in mode Stimmgerät, a tuner painted directly: note, cents needle eased from frame to frame, strobe, green within `kInTuneCents`) onto an image that fades by `persistence` each frame, plus pitch, peak/RMS meters and correlation; it is resizable and keeps its size in the state's properties `editorWidth`/`editorHeight`. Modes, triggers, channels, windows and colours are menus saved in projects: append only. Presets (`ScopePresets.cpp`, groups `kScopeCategories`) only set the view. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them (the processor reads `window` as the third): a new one goes at the end of both. Parameter ids start at version hint 1; the test app defines `TONWERK_SCOPE_NO_ENTRY`.

## Tonwerk Expander

A further plugin in the same CMake project: `TonwerkExpander` (instrument, `aumu TwEx Bvlp`, sources in `expander/src/`, tests in `tests/ExpanderTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. An eight-voice synth in the manner of the classic two-oscillator expander modules of the seventies; Marcel wants no brand named in its texts (name, UI, README, website), and nothing is copied. `ExpanderEngine.h` is plain C++ and borrows `Adsr`, `lfoShape`, `softClip` and `kDivisions` from `WaveDsp.h`: per voice two `Oscillator`s (saw, pulse or both; the pulse's mean taken out) whose steps get a polyBLEP at their exact time with the output a sample late, so oscillator 2's hard sync to 1 is smoothed like a wrap; `envPitch` sweeps oscillator 2 by the filter envelope. One TPT SVF per voice (`Svf`, band state held by a soft clip so full resonance stays bounded; damping 2 to 0.1, no self-oscillation), output lowpass and highpass weighted by `mode` and scaled so the louder is whole (notch in the middle), or `bandpass` (the band doubled, whole at the cutoff); `modeWeights`/`dampingFor` also feed the editor's curve. `drift` gives each voice fixed pitch and cutoff offsets seeded by its index plus a slow wander; poly takes the free voice after the last one (each with its place in the field), mono plays voice 0 legato, unison all eight at 1/sqrt(8). Pitch, cutoff and pulse width every 16 samples with ramps; keep it that way for CPU. Factory sounds (`ExpanderPresets.cpp`) are changes from the defaults, leveled to −12 LUFS by `PresetTests`, new ones at the end; `TONWERK_EXPANDER_WAV_DIR=<dir>` writes each sound's phrase. Waves and voice modes are menus saved in projects: append only. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them, the `fx*` ones left out: a new parameter goes at the end of both. Parameter ids start at version hint 1; the test app defines `TONWERK_EXPANDER_NO_ENTRY`. The editor's `Hardware-Blatt` saves the current patch as a PNG of a real expander module's knob positions as clock hours (`HardwarePanel.h`, plain C++: `panelFor` maps a `Settings` onto the hardware's knobs over estimated ranges, with notes on what does not carry over; `HardwareSheet.cpp` draws it; `tonwerkui::writeChosenData` saves it); `TONWERK_EDITOR_PNG_DIR` writes Sync-Lead's as expander-hardware.png, with `TONWERK_HARDWARE_ALL` every factory sound's.

## Tonwerk LFO

A further plugin in the same CMake project: `TonwerkLFO` (MIDI effect, `aumi TwLf Bvlp`, Logic's MIDI FX slot like Tonwerk Arp; no audio buses; sources in `lfo/src/`, tests in `tests/LfoTests.cpp` and `tests/MidiLearnTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. It sends a controller that an instrument's `MidiLearn` puts on a knob; Logic sends MIDI FX output only to the track's instrument, never to audio effects, so effects get their own LFO where it matters (Tonwerk Zone). `LfoEngine.h` is plain C++ and borrows Tonwerk Filter's shapes (`lfoValue`, `randomFor`, `kShapeNames`) and Wobble's divisions: value = centre ± depth/2, sent every `kStep` (64) samples when it changed, 14 bits (controller and controller + 32) for CC 0-31 when `fine`, else 7. `start` Song locks a synced cycle to the play head's ppq while playing; Note restarts it at the first key of a phrase (at its sample). Everything on the MIDI input passes. Presets (`LfoPresets.cpp`, groups `kLfoCategories`) never set `controller` or `channel`. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them: a new one goes at the end of both. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_LFO_NO_ENTRY`.

## Tonwerk Rumble

A further plugin in the same CMake project: `TonwerkRumble` (audio effect, `aufx TwRb Bvlp`, sources in `rumble/src/`, tests and its presets' levels in `tests/RumbleTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. The techno kick's rumble, made from the kick it sits on (no side chain): `RumbleEngine.h` is plain C++ and borrows `SvfStage` and `kDivisions` from `wobble/src/WobbleEngine.h`. The input summed to mono goes through a 12 dB lowpass (`tone`, the click out) into a hall (predelay, two allpasses, an eight-line FDN with Hadamard mixing, line gains from the RT60, lengths gliding over about 50 ms, wet times (1 − mean g²)^¼), an echo on the tempo (up to `kMaxEchoSeconds` 4 s, tanh in the loop) or the echo into the hall; then `Shaper` (soft, tube, hard, fold with first-order ADAA; made up so a sine at amplitude 0.25 keeps its RMS; the fold takes half the drive in dB), a 12 dB highpass (`lowCut`) and a 24 dB lowpass (Butterworth stage plus a resonant one, Q up to about 5, coefficients every `kControl` 16 samples). Ducking: a peak follower on the mono kick, falling 30 dB within `duckRelease`, mapped from `kDuckFloorDb` −42 to `kDuckFullDb` −12 dBFS onto `duck`, or with `duckSync` a (1 − t/release)² curve from each grid line of the play head's ppq (run on at the tempo while stopped); smoothed over 1 ms; `duckFilter` closes the lowpass by up to `kDuckOctaves` 3 with it. The rumble is mono and added to the untouched kick (`kick` at `kKickOffDb` −60 is off). The processor runs the engine in slices ending on 10 ms columns for the editor's history (`kickHistory`, `rumbleHistory`, `duckHistory`, atomics). Latency 0. Factory presets (`RumblePresets.cpp`, groups `kRumbleCategories` in `RumblePresets.h`) are leveled with `rumble` so kick plus rumble come across 3 dB (±2) louder than a kick on every beat at 120 BPM, −6 dBFS peak, under full scale; `TONWERK_RUMBLE_WAV_DIR=<dir>` writes those takes. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them: a new one goes at the end of both. Spaces, curves and divisions are menus saved in projects: append only. Parameter ids start at version hint 1; the test app defines `TONWERK_RUMBLE_NO_ENTRY`.

## Tonwerk Rig

A further plugin in the same CMake project: `TonwerkRig` (instrument, `aumu TwRg Bvlp`, sources in `rig/src/`, tests in `tests/RigTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others, and in the app's catalogue, so the effects can be played there. One instrument and `kSlots` (6) effects behind it, saved as one sound; the plugins inside are the other plugins' own processors (`RigCatalogue.cpp`: `instruments()`, `effects()`, ids saved in states: never rename one; not Robovox, Vocoder or the MIDI effects), so the target compiles `TONWERK_ALL_SOURCES` with every `*_NO_ENTRY` but its own, plus `TONWERK_SYNTH_NO_ENTRY` for Tonwerk Synth's entry. Everything that changes what is inside (`change()`: instrument, effects, sources, on/off, order) runs on the message thread under a spin lock after telling the editor (`Listener::rigWillChange`, so it deletes the inner editor, calling `editorBeingDeleted` first), the audio thread try-locks and plays silence when it misses. With Tonwerk Groovebox a slot's `source` 1 to 8 is a track: the rig turns on that track's output (`rebuild()`), runs the track's effects on it, delays every track and the main output to the slowest track's latency and adds them before the effects on the whole. Latency = instrument + that delay + the whole's effects, set after each change. No host parameters (they would change with the plugins inside); the instrument's MIDI learn reaches it. State: `TonwerkRig` XML, each plugin's own state as base64. Factory rigs (`RigPresets.cpp`, groups `kRigCategories`) name the plugins' factory sounds by program name; `RigTests` checks every name, and that the effects keep each rig within 3 dB of its instrument's own peak. The editor shows the chain (`ChainButton`s) above the chosen plugin's own editor and takes that editor's size. The test app defines `TONWERK_RIG_NO_ENTRY`.

## Conventions

- License: PolyForm Noncommercial 1.0.0 (`LICENSE`) with a `Required Notice:` attribution line in `NOTICE`, Marcel's choice from 2026-10-18 (no commercial use without his permission); up to 0.5.0 / commit c9ab322 it was AGPL-3.0. Distributed builds use JUCE under Marcel's own JUCE licence (Starter), which forbids open-source terms on JUCE products, so never bring in code whose licence requires releasing source (GPL, AGPL); permissive code (MIT, BSD, Apache) is fine.
- Commit messages and branch names are German; code and comments English; UI strings German.
- Comments explain why. Tests (`tests/`, JUCE `UnitTest`s run by `TonwerkSynthTests`) come with every change; DSP tests measure the sound (levels, duty cycle, envelope timing), not implementation details.
- 0.2.0 runs in Logic on Marcel's MacBook (his screenshot, 2026-10-01); anything newer has not been heard there unless a commit or the README says so. Say what was and was not tested.
- The website tonwerk.studio is `website/` (static, German, no web fonts or trackers), published by `website.yml` on GitHub Pages from main; every page has an English copy under `website/en/` with the same file name and anchor ids (pictures and style from the German side through `../`, `hreflang` links and a DE/EN switch in the top bar and footer of each), so a change to a page changes its copy in the same commit. `scripts/build-website.sh` adds `docs/*.png` as `img/` and fails when a page lacks its other-language twin, a picture is missing, or a plugin of `CMakeLists.txt` (but Tonwerk Synth) has no card (`<h3>Product Name</h3>`) in `index.html` or `en/index.html`, so a new plugin brings its card in both languages and its screenshot.
- Effects' standalone apps: every effect (`IS_SYNTH FALSE`, not the Arp) passes `${TONWERK_INPUT_PERMISSION}` to `juce_add_plugin`, which writes `NSMicrophoneUsageDescription`; macOS then asks once, without it the app hears silence and never asks (under the hardened runtime of a Developer ID build it also needs `scripts/app.entitlements`, audio-input). `build.yml` checks the text, and the entitlement when signed with the runtime, for every `aufx`/`aumf` app; a new effect needs the line.
- App icons: every `juce_add_plugin` (and `tonwerk_add_synth`) passes `ICON_BIG icons/<Target>.png`; JUCE turns it into the `.icns` (macOS bundles) and the `.ico` (Windows `.exe`) at configure time and stops when the file is missing. `scripts/make-icons.py` (Pillow) draws them all in one style (the favicon's cut panel, the sign yellow for instruments, cyan for effects, red for MIDI, red/cyan shifted beside it) plus 128 px copies in `website/icons/` for the cards; the PNGs are committed. A new plugin gets an entry in `ICONS` there. On Linux `package-release.sh` puts them in `Icons/` and `install-linux.sh` writes a `.desktop` entry per app (`StartupWMClass` is the app's name, JUCE's window class).
- `TONWERK_EDITOR_PNG_DIR=<dir>` makes the tests write a PNG of each synth (DX, Granular, Physical, Additiv, Groovebox, PD, Sampler, Bass, Neuro and Expander included), the distortion, the Robovox, the Vocoder, the Delay, the Chorus, the Glue, the Shimmer, the Filter, the Stutter, the Multiband, the Zone, the Scope (also scope-takt.png, scope-xy.png and scope-stimmgeraet.png), the Rumble, the Rig, the Wobble, the Tape, the Freeze, the Arp and the LFO editor, for looking at the UI without a Mac.
