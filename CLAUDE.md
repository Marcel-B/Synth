# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

Tonwerk Synth: the two browser synthesizers of Tonwerk (repository `Marcel-B/YuE-UI`, `src/YueUI.Api/ClientApp/src/logic/synth.ts`, `fm.ts`, `envelope.ts`, `effects.ts`) as JUCE instrument plugins for Logic Pro: Tonwerk Analog (`aumu TwAn Bvlp`) and Tonwerk FM (`aumu TwFm Bvlp`), plus Tonwerk Synth (`aumu Twsy Bvlp`), the first plugin with both engines, kept so Logic projects made with it still open. Audio Unit (v2 component, the format Logic loads), VST3 and a standalone app from one CMake project. README.md (German) is the user documentation.

## Commands

Requires CMake 3.22+ and a C++20 compiler; JUCE 8 comes through `FetchContent` (pinned tag in `CMakeLists.txt`). On Linux, JUCE needs the packages listed in `.github/workflows/build.yml`.

```sh
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Debug     # add -DFETCHCONTENT_SOURCE_DIR_JUCE=<clone> to reuse a local JUCE
cmake --build build --target TonwerkSynthTests && ctest --test-dir build --output-on-failure
cmake --build build --target TonwerkAnalog_Standalone     # also TonwerkFM_*, TonwerkDX_*, TonwerkSynth_*, *_VST3, *_AU (macOS only)
scripts/install-macos.sh                                  # on the Mac: Release build, ad-hoc signing, install, auval
```

The Mac has only the Command Line Tools, no Xcode: keep the build on CMake's default generators, never require the Xcode generator, an AUv3 app extension or a signing identity. Releases: pushing a tag `v*` runs `release.yml` (or starting it by hand with a version, which then makes the tag; the cloud sessions cannot push tags), which builds with `-DTONWERK_VERSION` from the tag, signs ad hoc, runs auval and attaches a zip (plugins, app, `scripts/install-release.sh` as `install.sh`, which removes the quarantine flag) to a GitHub release. CI (`build.yml`) runs the tests on Linux and on macOS, builds the universal AUs there, signs them ad hoc and runs `auval -strict -v` on every plugin. Warnings come from `juce_recommended_warning_flags`; keep the build free of them.

## Architecture

- `src/dsp/` is plain C++ without JUCE: `Patch.h` (the patch as Tonwerk's JSON describes it, both engines plus effects, and the TX81Z algorithm table), `Defaults.cpp` (Tonwerk's starting sound per track kind), `Ranges.h` (every range, the same as Tonwerk's `RANGES`, `FM_RANGES`, `EFFECT_RANGES`), `Envelope.h`, `Oscillators.h` (PolyBLEP oscillators, LFO, Web Audio's biquad, noise), `AnalogVoice.h`, `FmVoice.h`.
- The aim is to sound like the browser. Each DSP class says in its comment which Web Audio behaviour it reproduces (the pulse built from two sawtooths is half as loud as the plain square, lowpass/highpass Q is decibels, the envelope's time constants, FM in Hz with `kMaxIndex` 8, feedback averaged over two samples, reverb level 0.15). When Tonwerk's synths change, change both, and keep `PatchJson.cpp` reading their JSON.
- `PatchJson.cpp` reads and writes Tonwerk's patch JSON the way its `normalizePatch` does (missing fields take the melody's default, ranges clamp, `engine` absent means analog). Importing one engine keeps the other's settings.
- The three synth plugins are one set of sources built three times (`tonwerk_add_synth` in `CMakeLists.txt`, `TONWERK_EDITION`); `TonwerkSynthProcessor(Edition)` decides. Each descriptor has a `Part` (engine switch, analog, fm, effects, from its id); an edition gets only its parts' parameters (`createParameterLayout(edition)`), `ParameterReader` leaves the missing fields at their defaults, and the one-engine editions force `patch.engine`. Their state roots are `TonwerkAnalog` / `TonwerkFM`; Tonwerk Synth keeps `TonwerkSynth`. Factory sounds per edition (`PresetLibrary::factoryPresets(edition)`): Tonwerk's four per engine first, then the plugin's own (`FactorySounds.cpp`, plain C++, new ones at the end); Tonwerk Synth keeps its first eight program numbers. The imported library is shared, `importedFor(edition)` filters by engine.
- `Parameters.cpp` has one table (`descriptors()`) of every patch field as a host parameter; layout, reading a `Patch` from the parameters each block (`ParameterReader`) and writing an imported patch (`writePatch`) all come from it. A new field is one entry there. Parameter ids are part of saved Logic projects: never rename or remove one, and append new ones with the version hint of the release they first appear in (2 for 0.2.0, 3 for 0.3.0).
- `PluginProcessor.cpp`: a `juce::Synthesiser` with 16 `SynthVoice`s rendering mono into a buffer, then `EffectsChain` (delay, `juce::dsp::Convolution` reverb) into stereo. Voices read the shared patch every block, so knobs act on sounding notes. The reverb's impulse is made on the message thread (timer), never on the audio thread.
- Wavefolder and sample and hold (`AnalogPatch::fold`, `sampleHold`; `Wavefolder`, `SampleHold` in `Oscillators.h`) are the plugin's own, not Tonwerk's: the folder sits between the oscillator mix and the filter, the sample and hold moves cutoff and pitch per voice. Both are off at their defaults, `patchToJson` writes them only when on, and a Tonwerk sound imports with them off.
- Tempo sync (`dsp/Tempo.h`, `withTempo`): the processor turns a synced LFO's or sample and hold's note value into a rate and a synced delay's into a time, from the play head's BPM (120 without one), before the voices and effects see the patch; the DSP knows only rates and times. Sync and division are this plugin's own fields; Tonwerk's JSON lacks them, `patchToJson` writes them only when sync is on.
- `ScopeBuffer` (`common/ScopeBuffer.h`, a processor member) holds the last 4096 output samples as atomics; `ScopeView` (`common/NightCity.h`) reads them at 30 Hz and triggers on a rising zero crossing, as Tonwerk's `SynthScope.vue` does.
- `common/NightCity.{h,cpp}` is the look every plugin but Chrome Glitch uses (Tonwerk Wavetable's): colours, `LookAndFeel`, `Control` (knob, menu or switch for a parameter), `Section` (panel of rows, optional power switch and display room on the left or on top, `when` to swap a rate knob for its note value), `layoutRow` (spare width goes to panels with a display), `ScopeView`. Values are shown by the parameters' own text functions: whole numbers with units.
- Factory sounds of all five synths carry a category from `common/PresetCategories.h`; the editors' menus group by it (`menuOrder`), the program numbers stay in release order. `tests/PresetTests.cpp` plays each with a phrase of its category and holds it to one loudness (EBU momentary max: −12 LUFS, Tonwerk DX −16 because a voice ends at half of full scale, ±2 dB, effects up to 6 dB lower) and a peak under 1.0 with delay and hall; Tonwerk's own starting sounds and Init are exempt. A new sound is leveled with its volume (DX also against `DxTests`' hard chord). `TONWERK_PRESET_WAV_DIR=<dir>` writes each phrase as a WAV, `TONWERK_TEST_CATEGORY=Presets` runs only that category. The hall seeds its noise with the room size, so a sound measures and bounces the same every time; the test waits for the convolution to take the room over (`roomPlaying`).
- `common/EffectPresets.{h,cpp}`: the effects' factory sounds as host programs (`EffectPrograms`, a sound names only what it changes from the defaults, its name kept in the state as `presetName`) and the header's preset menu with arrows (`PresetBar`). `tests/EffectPresetTests.cpp` (category Presets) checks and levels them; `TONWERK_PRESET_WAV_DIR` writes their takes and the dry sources.
- `PresetLibrary.cpp`: factory sounds (the host's programs) and imported ones in `presets.json` under Application Support, plus Tonwerk's address in `settings.json`. `fetchFromTonwerk` calls Tonwerk's `GET /api/logic/synths/presets` (no login, reached over Tailscale).
- `PluginEditor.cpp`: sections per engine (envelope displays, the FM algorithm drawn by `AlgorithmView`), the engine switch for Tonwerk Synth only (its editor resizes per engine), the preset menu and the import/export buttons, an on-screen keyboard and the scope. Strings with umlauts go through `utf8()` / `String::fromUTF8`, since `juce::String` reads a plain `const char*` as ASCII.

## Chrome Glitch

A second plugin in the same CMake project: `ChromeGlitch` (audio effect, `aufx ChGl Bvlp`, sources in `glitch/src/`, tests in `tests/GlitchTests.cpp` inside `TonwerkSynthTests`). It is built, signed, validated with auval, installed and released alongside the synth. `GlitchEngine.h` is plain C++: ticks (grid lines of the host tempo in sync, random 40-250 ms gaps otherwise, the chaos share of those also in sync) roll for a stutter (replays the last slice, later repeats maybe pitched, never wrapping inside a repeat) or a dropout; every change crossfades over 1.5 ms; the crusher is full during a glitch and light between. While the host plays with a position, the dice (and the crusher's hold phase) reseed at every beat from the `seed` parameter and the beat number, so a glitch belongs to its place in the song whatever the start point; without a position they seed once per transport start. Its parameter ids follow the same never-rename rule; they start at version hint 1 (`seed` has 2). The test app defines `CHROME_GLITCH_NO_ENTRY` because both plugins define `createPluginFilter`. The editor uses Cyberpunk 2077's colours (yellow, cyan, red on near black); its `GlitchMonitor` reads `glitching`, `glitchStarted` (set by the processor whenever `GlitchEngine::eventsStarted()` grows, taken back by the editor's 30 Hz timer, so a glitch shorter than a frame still shows) and `lastEvent`. The monitor's texts (CHROME OK, INTERFERENCE, NO SIGNAL, FROZEN) are English on Marcel's wish, the one exception to German UI strings. Factory presets (`GlitchPresets.cpp`, groups `kGlitchCategories`) are tested to glitch on a voice, never louder than it and at most 3 dB quieter.

## Tonwerk Distortion

A third plugin in the same CMake project: `TonwerkDistortion` (audio effect, `aufx TwDs Bvlp`, sources in `distortion/src/`, tests in `tests/DistortionTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the other two. `Ds1Circuit.h` is plain C++: BOSS DS-1's circuit with ElectroSmash's part values, in volts (1.0 = 1 V at the jack). `Drive` (booster, op-amp stage, rails, diode clipper from a Shockley table) runs 4x oversampled through `juce::dsp::Oversampling` (polyphase IIR) with first-order ADAA on both clippers; `Voice` (tone blend, level, DC block) runs at the host rate. The op-amp's slew rate is deliberately left out (it aliased more than all the clipping). Keep CPU low: the test logs the real-time factor. The editor (Night City) shows `scopeOut` over `scopeIn`, the input read `getLatencySamples()` behind. Factory presets (`DistortionPresets.cpp`, groups `kDistortionCategories`) are leveled with `level` to match their dry source (a test signal of their group peaking at -6 dBFS) within 2 dB. Parameter ids start at version hint 1; the test app defines `TONWERK_DISTORTION_NO_ENTRY`.

## Tonwerk Wavetable

A fourth plugin in the same CMake project: `TonwerkWavetable` (instrument, `aumu TwWt Bvlp`, sources in `wavetable/src/`, tests in `tests/WavetableTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. A wavetable synth in the manner of Serum, for dubstep basses; nothing of Serum's (tables, presets, art) is copied. `Wavetables.cpp` computes every table from a formula at load (64 frames, one band-limited copy per octave, shared by all instances); `WaveDsp.h` and `WaveEngine.h` are plain C++ (envelopes, LFOs, TPT state variable filter, comb, voices, poly/mono/legato, matrix). Modulation runs every 32 samples with ramps in between; keep it that way for CPU. The sub oscillator and noise come from `src/dsp/Oscillators.h`. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them: a new parameter goes at the end of both. Factory sounds are in `WavetablePresets.cpp` as changes from the defaults. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_WAVETABLE_NO_ENTRY`.

## Tonwerk DX

A fifth plugin in the same CMake project: `TonwerkDX` (instrument, `aumu TwDx Bvlp`, sources in `dx/src/`, tests in `tests/DxTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. Six operators in the DX7's 32 algorithms (Tonwerk FM stays at four so Tonwerk's JSON stays 1:1). `DxEngine.h` is plain C++ in the DX7's units: levels and rates 0 to 99, a level step 0.75 dB, envelopes in the log domain, envelopes and LFO every 32 samples with gain ramps between, a sine table; keep it that way for CPU. `lfoHz` is fitted to DX7/TX7 measurements (speed 35 about 5.6 Hz, 99 about 49 Hz), so SysEx vibratos run at their speed. `DxSysex.h` reads DX7 banks and single voices the user owns (pitch EG, keyboard level scaling and fixed frequencies are dropped); imported files live in Application Support/Tonwerk DX/SysEx. Factory sounds (`DxPresets.cpp`) are the plugin's own, never copies of Yamaha's ROM; new ones go at the end. `DxProcessor.cpp` has one table (`parameters()`) of every patch field; ids start at version hint 1. The delay and hall are the synth's `EffectsChain`. The test app defines `TONWERK_DX_NO_ENTRY`.

## Tonwerk Granular

A sixth plugin in the same CMake project: `TonwerkGranular` (instrument, `aumu TwGr Bvlp`, sources in `granular/src/`, tests in `tests/GranularTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. `GrainSources.cpp` computes nine sources from formulas at load (4 s each at 48 kHz, root C4, shared by all instances) plus copies at half, quarter, ... rate, each lowpassed, so a grain read faster than its source takes the copy that keeps it below Nyquist; the user's file (`loadFile`, first 30 s, mono) gets the same treatment, its path is in the state (`sampleFile`) and is read again on load, the samples are not saved. The message thread swaps the user's source under a spin lock, the audio thread takes it with a try-lock, and a replaced source waits in `retired` until only that list holds it, so the audio thread never frees one. `GranularEngine.h` is plain C++ and borrows `Adsr`, `SvfStage` and `lfoShape` from Tonwerk Wavetable's `WaveDsp.h`: up to 40 grains per voice, windows from tables, a cloud's level scaled by 1/sqrt of the overlap so density and size keep the loudness, modulation every 32 samples, fixed routes (two LFOs, envelope 2, wheel, velocity) to one target each. A grain's start is chosen so it fits in the source without wrapping. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them, the `fx*` ones (Tonwerk DX's ids, read apart) left out: a new parameter goes at the end of both. Delay and hall are the synth's `EffectsChain` with its stereo overload. Factory sounds (`GranularPresets.cpp`) are changes from the defaults, leveled to −12 LUFS by `PresetTests`. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_GRANULAR_NO_ENTRY`.

## Tonwerk Physical

A seventh plugin in the same CMake project: `TonwerkPhysical` (instrument, `aumu TwPh Bvlp`, sources in `physical/src/`, tests in `tests/PhysicalTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. `PhysicalEngine.h` is plain C++ and borrows `Adsr`, `SvfStage` and `lfoShape` from `WaveDsp.h`: an exciter (pluck, strike, bow, blow) drives a resonator. String and tubes are waveguides (two delay lines meeting at the excitation point, Lagrange fractional delay, a one-pole loss filter set from two T60s, four allpasses for a stiff string's stretch, the loop's delay compensated so the note stays in tune); the bow is a friction curve on the string's velocity, the reed a pressure curve on a closed tube. Bar, bell, membrane and bowl are up to 16 two-pole resonators from `modeTable`. `levelOf` and the drive normalisation keep every exciter on every resonator within a few dB of each other at the defaults; tests hold each pairing finite and bounded at the extremes. Modulation every 32 samples with ramps; keep it that way for CPU. Enum orders are menu orders saved in projects: append only. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them, the `fx*` ones (Tonwerk DX's ids) left out: a new parameter goes at the end of both. Factory sounds (`PhysicalPresets.cpp`) are changes from the defaults, leveled to −12 LUFS by `PresetTests`, new ones at the end. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_PHYSICAL_NO_ENTRY`.

## Tonwerk Groovebox

An eighth plugin in the same CMake project: `TonwerkGroovebox` (instrument, `aumu TwGb Bvlp`, sources in `groovebox/src/`, tests in `tests/GrooveboxTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. A drum machine: eight synthesised instruments (no samples) and a step sequencer. `GrooveEngine.h` is plain C++ and borrows `Biquad`, `Noise` and `BlepOscillator` from `src/dsp/Oscillators.h`: each `Voice` builds its instrument the way the analog drum machines do (falling sine for kick and toms, body plus filtered noise for the snare, noise bursts for the clap, six squares at the 808's ratios band-passed for hats and cymbal), `decay` is the time to -60 dB; each track has two voices so a new hit lets the last fade over 5 ms; the closed hat chokes the open one. `Clock::steps` counts steps from the song's beat 0 (so patterns sit on the host's bars, whatever the start or loop), swing delays every odd step. The processor runs it from the play head's ppq (`seqMode` host, only while playing), from its own beat counter (free) or not at all; a block that starts within half a sample of the last one's end continues it, so a step on the seam plays once. MIDI notes play tracks on General MIDI's drum notes (`trackForNote`). Patterns are not parameters: eight per instance, in atomics (on bits low, accent bits high) and in the state as child `Patterns`; the editor's edits call `patternsChanged()` so the host marks the project modified. Per-track delay and hall sends go through `EffectsChain`'s send overload. Kits (`GroovePresets.cpp`, groups `kGrooveCategories`) name parameter changes and patterns as text (`x`, `X` accent, `.`); choosing one resets everything but `seqMode`. `GrooveboxTests` plays two bars of each kit's pattern A and holds it to -16 LUFS momentary ±2 dB with the peak under 1.0 (drums peak about 15 dB over their loudness), new kits at the end. Parameter ids (`kick`, `snare`, `clap`, `tomLow`, `tomHigh`, `hatClosed`, `hatOpen`, `cymbal` + `Tune`, `Decay`, ...) and menu orders start at version hint 1; the test app defines `TONWERK_GROOVEBOX_NO_ENTRY`.

## Tonwerk Robovox

A ninth plugin in the same CMake project: `TonwerkRobovox` (music effect, `aumf TwRv Bvlp`, so Logic can send it MIDI through the side chain; sources in `robovox/src/`, tests in `tests/RobovoxTests.cpp` inside `TonwerkSynthTests`, its presets in `EffectPresetTests`), built, signed, validated, installed and released like the others. The robot voice of AI songs, from Marcel's example (a stem of "Day Off in Night City"): a vocoder whose carrier is a low, steady note stepping without glide (D1 and G1 there, the bass line, hence the stem splitter calling it bass), the voice's formants over its dense comb. `RobovoxEngine.h` is plain C++ and borrows `BlepOscillator` and `Noise` from `src/dsp/Oscillators.h`: `PitchTracker` (YIN on a copy lowpassed at 1 kHz and decimated to about 12 kHz, 25 ms window, every hop), `Quantiser` (nearest scale note, 0.3 semitone hysteresis, a new note must be read twice), and an STFT vocoder (frame about 21 ms, 1024 at 48 kHz, Hann, hop a quarter; voice and carrier share one complex FFT; the carrier is whitened by its own envelope, smoothed at least as wide as its harmonic spacing, and takes the voice's, smoothed over `bandwidth`; formant shift reads the envelope at k/ratio; `bass` keeps the carrier's lowest harmonics up under the voice; a frame mostly above 4 kHz turns the carrier to noise by `sibilance`). The voice reaches the vocoder half a frame late so the carrier's pitch (read from the undelayed voice) changes with its syllable; MIDI notes are delayed by the same amount. Latency a frame and a half (1536 at 48 kHz), the dry path delayed to match. Mono inside. For MIDI it goes in a software instrument track's instrument slot (AU MIDI-controlled effects) with the voice's track as its side chain, which Logic feeds to the first input bus; an audio FX slot gets no MIDI and shows no side chain menu. In MIDI mode a released key keeps its note (the voice decides when it sounds); before any note the voice drives the carrier. Note names in the UI follow Logic (C3 = 60). Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_ROBOVOX_NO_ENTRY`.

## Tonwerk Wobble

A tenth plugin in the same CMake project: `TonwerkWobble` (audio effect, `aufx TwWb Bvlp`, sources in `wobble/src/`, tests in `tests/WobbleTests.cpp` inside `TonwerkSynthTests`, its presets there too in category Presets), built, signed, validated, installed and released like the others. A filter and a volume shaper, each moved by an LFO whose curve the user draws, for dubstep wobbles. `WobbleEngine.h` is plain C++: `Curve` (corners x/y 0 to 1, ends pinned to x 0 and 1, two at one x make a step, a power-curve bend per segment up to exponent 8 either way, `bendThrough` its inverse for the editor; text "x y bend;..." in the state), `CurveTable` (1024 atomics the message thread fills, the audio thread reads), TPT state variable filters (12/24 dB; resonance from Q 0.7 to about 17), the vowel filter (three bandpasses gliding u-o-a-e-i with the curve), smoothing per sample, filter coefficients every 8 samples. The processor puts a synced LFO where the play head's ppq says while playing and runs it on at the tempo otherwise. Curves are not parameters: `filterCurve` / `volumeCurve` on the state's root, `setCurve` calls `updateHostDisplay` with a non-parameter change. Presets (`WobblePresets.cpp`, groups `kWobbleCategories` in its header to keep `PresetCategories.h` free of it) name parameter changes plus both curves (`factoryCurves()`, empty means the lane's default); choosing one in `setCurrentProgram` draws them. Leveled with `output` against a held bass (wobbles, vowels) or a pad at 140 BPM within 2 dB. Enum and division orders are menu orders saved in projects: append only. Parameter ids start at version hint 1; the test app defines `TONWERK_WOBBLE_NO_ENTRY`.

## Tonwerk PD

An eleventh plugin in the same CMake project: `TonwerkPD` (instrument, `aumu TwPd Bvlp`, sources in `pd/src/`, tests in `tests/PdTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. Phase distortion as on Casio's CZ synths; no Casio ROM sounds. `PdEngine.h` is plain C++ and borrows `Adsr` and `lfoShape` from `WaveDsp.h`: `pdWave` reads a table cosine through a bent phase, eight waves (saw, square, pulse, double sine, saw-pulse, three windowed resonances up to 16 times the note), every one but the resonances a cosine at bend 0, all starting each cycle at 1 so alternating waves (`Welle 2`, cycle by cycle as on the CZ) never step. Two lines with their own DCW and DCA envelopes; `lines` picks 1, 2, 1+1' (line 1 again at line 2's detune) or 1+2'; ring multiplies line 2 by line 1, noise reads line 2 at a wandering phase. Aliasing is held down by never letting a fall take less than about two samples (`steepest`) and a polyBLEP on the double sine's steps; tests log what folds back at C7. Each line is a quarter of full scale, so presets sit near 0 dB master. A stereo `Chorus` after the voices, then `EffectsChain`. Modulation every 32 samples with ramps, envelopes per sample. Enum orders are menu orders saved in projects: append only. `readSettings()` reads the parameters in the order `createParameterLayout()` adds them, the `fx*` ones left out: a new parameter goes at the end of both. Factory sounds (`PdPresets.cpp`) are changes from the defaults, leveled to −12 LUFS by `PresetTests`, new ones at the end. Parameter ids and menu orders start at version hint 1; the test app defines `TONWERK_PD_NO_ENTRY`.

## Tonwerk Tape

A twelfth plugin in the same CMake project: `TonwerkTape` (audio effect, `aufx TwTp Bvlp`, sources in `tape/src/`, tests and its presets' levels in `tests/TapeTests.cpp` inside `TonwerkSynthTests`), built, signed, validated, installed and released like the others. A worn tape machine for lo-fi. `TapeEngine.h` is plain C++: record (input gain, a 6 dB pre-emphasis shelf, a biased tanh with first-order ADAA scaled so a ±0.25 swing keeps its level at any drive, the exact inverse shelf, triangular hiss per channel, the dropout gain), a ring buffer read `kCentreSeconds` (8 ms) behind on a cubic at the offset `Motion` gives (wow 0.55 Hz with drifting rate plus 0.23 Hz, flutter 7.3 and 12.1 Hz, shared by both channels), then the playback head (type's highpass and bump, the dictaphone's ceiling, the tone lowpass). The dry path is read from its own ring at the same 8 ms, reported as latency. Wobble, dropouts and hiss reseed from a fixed seed on every transport start, so a bounce repeats. Tape types (`TapeType`, `characterOf`) are a menu saved in projects: append only. Parameter ids start at version hint 1; the test app defines `TONWERK_TAPE_NO_ENTRY`. Factory sounds (`TapePresets.cpp`, groups `kTapeCategories`) are leveled with `output` to a lo-fi beat at −6 dBFS peak within 2 dB.

## Conventions

- Commit messages and branch names are German; code and comments English; UI strings German.
- Comments explain why. Tests (`tests/`, JUCE `UnitTest`s run by `TonwerkSynthTests`) come with every change; DSP tests measure the sound (levels, duty cycle, envelope timing), not implementation details.
- 0.2.0 runs in Logic on Marcel's MacBook (his screenshot, 2026-10-01); anything newer has not been heard there unless a commit or the README says so. Say what was and was not tested.
- `TONWERK_EDITOR_PNG_DIR=<dir>` makes the tests write a PNG of each synth (DX, Granular, Physical, Groovebox and PD included), the distortion, the Robovox, the Wobble and the Tape editor, for looking at the UI without a Mac.
